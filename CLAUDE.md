# Horde: guidance for contributors and AI coding agents

Horde is a self-hosted video library and downloader with accounts (one admin plus members; trusted LAN). One FastAPI process serves the JSON API, streams media, runs background workers and hosts the built React SPA.

## Architecture

Start with `docs/design/architecture.md` (one-page map) and the decision records in `docs/adr/` (why SQLite, threads, the auth model, the CSRF header, the error envelope, the downloader split, FTS5 triggers, releases).

- `backend/app/main.py`: FastAPI app and `lifespan`. Startup order: build and activate the `AppContext`, create dirs, `init_db`, orphan cleanup, then `_start_workers`, which starts the download queues and runs queue recovery (`download_queue.recover()`, `recover_ai_jobs`, `recover_catalog_jobs`) before the other loops. Shutdown signals every worker and joins them in reverse start order.
- `backend/app/api/`: one router per area (`videos`, `video_ai`, `video_media`, `downloads`, `preview`, `stream_ai`, `review`, `playlists`, `channels`, `app_settings`, `ai`, `system`, `setup`, `auth`, `users`, `backgrounds`, `fonts`, `compat`). Routers stay thin; logic lives in services. `app/security.py` holds the middleware stack (`build_stack`), `app/auth.py` the auth middleware and dependencies, `app/errors.py` the error envelope.
- `backend/app/services/`: all business logic. Notable modules: `downloads/` (package: `queue`, `runner`, `ffmpeg_queue`, `postprocess`, `finalize`, `jobs`, `playlist_import`, `progress`, `staging`, ...; import these directly), `workers` (`WorkerRegistry`), `pagination` (cursors), `health` (`/api/ready`), `scanner` (watchdog + poll of `DOWNLOADS_DIR`), `library`, `metadata`, `sprites`, `thumbnails`, `compat_rendition` (H.264 sidecars), `stream_preview` (DASH preview of not-yet-downloaded videos), `stream_ai` / `stream_related` (AI results and related videos for a stream; saved per YouTube id, moved onto the video on download, expired after `HORDE_STREAM_AI_RETENTION_DAYS`), `app_settings` (JSON settings), `auth/` (accounts, sessions, permissions, signed media URLs), `user_state` / `user_settings` (per-user history and UI preferences), `ai/` (embeddings, `vector_index`, tags, chapters, chat, `help_chat` (Ask about Horde over the shipped docs and source; `help_catalog.json` lists the settings it may link or change, `help_data` the user data it may read), one OpenAI-compatible provider with Ollama/OpenRouter extras, cost ledger), `channel_catalog/` (channel indexing).
- Workers are daemon threads started in `lifespan` through one `WorkerRegistry` (`app.state.workers`; feeds `/api/ready` and `/api/metrics`): scanner, metadata sync, AI (single-flight), channel catalog (one at a time), channel autodownload, subtitle retry, stream AI (carry-over and expiry), job metadata, plus the download queue's own pool. They are skipped when `HORDE_E2E` is set.
- `backend/app/models.py` (SQLModel tables and status enums), `schemas.py` (request/response models), `config.py` (env-derived tunables), `context.py` (`AppContext`: paths, engine, queues, workers, auth; `get_ctx` / `get_session` / `get_paths()` / `get_engine()`), `database.py` (engine factory, WAL, migrations).
- DB: SQLite at `DATA_DIR/horde.db`, schema managed by Alembic (`backend/app/migrations/`, batch mode, foreign keys enforced). `init_db()` upgrades to head at startup: fresh DB -> `upgrade head`; pre-Alembic DB -> frozen `legacy_migrations.py` then `upgrade head`; unknown (newer) revision -> refuse to start. Delete videos only through `services/video_delete.delete_video_cascade`. `video_tags` and the `videos_fts` FTS5 index are derived by SQLite triggers and `videos.youtube_id` by a mapper listener: never write them directly, and a revision that rebuilds `videos` or `video_ai_meta` must recreate the triggers and refill `videos_fts` (`docs/design/sqlite-and-migrations.md`).
- `frontend/src/`: React 18 + TypeScript + Vite + Tailwind. `pages/` (Library, Watch, Download, Import, Playlists, History, Settings, Setup, Offline, Login, CreateAdmin), `components/` (`components/auth/` incl. `RequirePermission`), `context/` (Auth, Playback, Download, Search, Toast, Confirm providers), `queries/` (TanStack Query hooks and keys; server data is read through these), `hooks/`, `api.ts` (the entry point: re-exports and assembles the `api` object from the per-area modules in `api/`, with the fetch core and `ApiError` in `api/client.ts`) and `api/schema.d.ts` (generated from `backend/openapi.json` by `npm run gen:api`; `types.ts` aliases it), `offline/` (service worker, IndexedDB, offline downloads), `types.ts`.
- `frontend/e2e/` Playwright specs; `e2e/serve.py` starts the app with a seeded temporary library (`HORDE_E2E=1`, ports 8091 app / 8092 setup wizard; override with `E2E_APP_PORT` / `E2E_SETUP_PORT`).
- `docs/` is the MkDocs wiki (also shipped at `/wiki`; `docs/adr/` holds the decision records); `docker/` and `Dockerfile` build the single-container image.

## Working style

These bias toward caution over speed; use judgment on trivial tasks. The project rules in the gate and conventions below take precedence where they are more specific.

- Think before coding. State your assumptions. If a request has several readings, say which you took instead of picking silently; if a simpler approach exists, say so and push back when warranted. When a wrong guess would be costly (a migration, deleting data, auth or security, a public API change, anything hard to reverse), stop and ask. For low-stakes ambiguity (small, contained, easy to redo), pick the most reasonable reading, note the assumption in your summary and keep going.
- Simplicity first. Write the minimum code that solves the problem: no features, options or configurability that were not asked for, and no abstraction that has one caller (the router/service split above is a project structure rule, not a speculative abstraction). Do not add defensive checks for states your own code makes impossible; an `assert` documents an invariant. Always handle failure at system boundaries: user input, file and network I/O, `yt-dlp`/`ffmpeg` subprocesses, external APIs (YouTube, OpenRouter, Ollama), parsing untrusted data, and disk or memory limits. Those fail in practice, and the logging rules under Conventions apply to how you handle them. If 200 lines could be 50, rewrite it.
- Surgical changes. Every changed line should trace to the request, to a change these rules require (docs, `openapi.json`, `schema.d.ts`, a migration) or to a bug fix you called out. Do not reformat, restyle or refactor adjacent code that is not broken (formatter output on lines you touched is fine), and match the existing style. Remove imports and helpers your change made unused; mention pre-existing dead code instead of deleting it.
- Bugs you run into. If a bug in nearby code blocks your task or breaks your change, fix it with the smallest change that works, in its own commit with a regression test, and call it out in your summary. If it is unrelated, do not silently fix or ignore it: report the file, location, what is wrong and a suggested fix. Always flag security issues, data-loss risks and crashes prominently.
- Goal-driven execution. Turn the task into something checkable before you start: a bug fix starts with a test that reproduces it (end-to-end or `TestClient` first, per Conventions), validation starts with tests for the invalid inputs, a refactor keeps the affected tests green before and after. For multi-step work, state a short plan with how each step will be verified, then loop until the checks pass.

## Mandatory gate

Test in proportion to the work. While working, run only the checks that cover what changed: the touched files' lint/format/types, the affected `pytest` files (`pytest tests/test_x.py -k ...`), and the affected Playwright specs (`npx playwright test e2e/x.spec.ts`). Run the full `scripts/check.sh` (with `--e2e` when you touched UI or API behaviour the UI uses) once at the end of a task or long session, before the final push, not before every commit. Subagents run only the targeted tests for their own change, never the full gate or the whole e2e suite, and only one Playwright run at a time (they share ports 8091/8092).

Review in proportion to the change too. A small, local change (a style tweak, a one-function fix, copy, a test) needs no separate reviewer: a regression test that fails before and passes after, plus your own reread of the diff, is enough. Give a change an independent critical review (a reviewer agent that assumes it is broken) when it is large or risky: a schema migration, auth or security code, a new API surface, concurrency, data deletion, or a multi-file feature. One review pass, then fix its findings; do not re-review the fixes unless they are themselves large. `scripts/check.sh` runs, in order: `ruff check`, `ruff format --check`, `mypy`, the `requirements.lock` check (`scripts/check_requirements_lock.py`), the committed `backend/openapi.json` check, `pytest`, the generated `api/schema.d.ts` check, `eslint --max-warnings 0`, `prettier --check`, `tsc`, `vitest`, `vite build`, `mkdocs build --strict`. CI runs the same gates; a red gate is never acceptable to merge. Details: `docs/getting-started/testing.md`.

Backend commands (from `backend/`): `PYTHONPATH=. pytest -q -n auto --durations=20` for the whole suite (pytest-xdist; tests must stay isolated across worker processes), plain `pytest tests/test_x.py` for one file, `ruff check .`, `ruff format .`. Frontend (from `frontend/`): `npm run lint`, `npm run format`, `npm run typecheck`, `npm test`, `npm run build`. `mypy` (from `backend/`, config in `pyproject.toml`) is a gate and must report zero errors.

## Conventions

- No new broad `except Exception` without logging the error (`logger.exception` / `logger.warning(..., exc_info=True)`). Silent `pass` handlers are not acceptable and none remain: `tests/test_code_conventions.py` fails on any `noqa: S110` / `SIM105` or a `noqa` without a reason, and ruff (`S110`, `BLE001`) has no per-file exemptions. Log at `debug` for routine, noisy failures and `warning` otherwise, with `exc_info=True`.
- Every `# noqa` and `// eslint-disable` needs a reason after ` - ` / ` -- `. Fix the finding instead whenever it is cheap.
- Types: `mypy` stays at zero errors. Annotate for real and narrow optionals with an actual check; a `# type: ignore[code]  # reason` (specific code, reason after the second `#`, which mypy requires) is for an unavoidable library typing gap only (`tests/test_code_conventions.py` enforces the form). SQLModel class attributes are typed as their Python values: build SQL expressions with `col(Video.id)`, and read a primary key that must be set with `require_id(row)` (`models.py`).
- No new module-level mutable state in new code (module dicts/sets/locks that tests have to reset). Hold state on the `AppContext` (or an object it owns), so tests can build a fresh one. Never import a directory or the engine at module level: use `get_paths()` / `get_engine()` or `ctx` (`docs/design/app-context.md` lists the state that remains and why).
- New endpoints declare `response_model` (and request models in `schemas.py`); do not return ad-hoc dicts. Errors use the one envelope `{detail, code, ...}` (`raise CodedHTTPException(status, detail, "code")`; clients branch on `code`); lists return `{items, next_cursor}` via `services/pagination.py`. Any API change regenerates the committed schema: `cd backend && PYTHONPATH=. python -m app.export_openapi openapi.json` (the gate fails when it is stale). No `/api/v1` prefix (`docs/adr/0005-error-envelope-and-cursors.md`).
- Schema changes are Alembic revisions: edit `models.py`, run `cd backend && alembic revision --autogenerate -m ... --rev-id NNNN_name` against a scratch `DATA_DIR`, review it, never edit an existing revision. `tests/test_database_migrate.py` fails when models and revisions drift. See `docs/design/sqlite-and-migrations.md`. Never edit the DB by hand in code paths.
- Prefer end-to-end tests: Playwright for UI behaviour, FastAPI `TestClient` for API behaviour. Add a unit test for a real bug regression or pure logic. Never skip or weaken a test to get green; fix test isolation instead.
- Tests must be order independent. Background threads started by a test must be joined before it ends (see the autouse fixture in `backend/tests/conftest.py`).
- UI design: `PRODUCT.md` (who Horde is for, product principles) and `DESIGN.md` (colors as theme roles, type, spacing, components, motion) at the repo root describe the current design system. Follow them for UI work and update `DESIGN.md` in the same change when the system itself changes.
- Frontend: fix `react-hooks/exhaustive-deps` properly; an intentional omission needs a disable with a `-- reason`. Clickable non-button elements need a role and keyboard handling; form controls need an associated label.
- Security (details: `docs/ops/security.md`, `backend/app/security.py`): every non-GET request needs the `X-Horde-Request` header. `frontend/src/api.ts` adds it automatically; any new `fetch` / `XMLHttpRequest` that mutates must use `withCsrf()` / `CSRF_HEADER`, and tests that call the API directly send it too (the `client` fixture does). No destructive GETs: a GET only serves what exists. User-supplied URLs go through `services/url_safety.py`, uploads through `services/uploads.py`, and links rendered from stored data through `safeHref()`. Middleware order lives in one list (`build_stack`); auth slots in after `CsrfMiddleware`.
- Auth: every `/api` route is protected by default (`AuthMiddleware`, `app/auth.py`); only the exact list in `PUBLIC_ROUTES` is open. Routes that change server-wide state declare `dependencies=[Depends(require_admin)]`; routes a member may only use with a grant declare `require_permission("...")` (names in `services/auth/permissions.py`). `tests/test_permissions.py` fails when a mutating route is not classified. Get the user with `Depends(current_user)`; never trust a client-supplied user id.
- Watch history is per user: read and write `user_video_state` (`services/user_state.py`), pass `user_id` to `library.query_videos` and `video_serialize.to_read`. Never read or write `videos.last_position_sec` / `videos.last_watched_at` (legacy columns, kept only so the first admin can adopt them). AI chat messages carry `user_id`.
- Update `docs/`, `README.md` and `.env.example` in the same change when behaviour or configuration changes. A notable decision gets a short record in `docs/adr/` (Context / Decision / Consequences), listed in `docs/adr/index.md` and `mkdocs.yml`.
- Releases: a `vX.Y.Z` tag on a green `main` is what ships to users (`update.sh` follows releases by default and rolls back a failed update); see `docs/development/release-process.md`.
- Commits: small, one concern each, imperative subject under 72 characters, a body explaining why. Mechanical reformatting goes in its own commit.
